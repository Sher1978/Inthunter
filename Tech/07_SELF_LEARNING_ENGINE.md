# 07. Архитектура Самообучающегося ИИ-Движка (AI Training Engine)

Этот документ описывает двухуровневую систему памяти (Two-Level Memory System) для ИИ-Анализатора, которая позволяет системе самообучаться на основе ручных корректировок администратора (Human Feedback), не переполняя контекстное окно LLM.

## Проблема
При ручном исправлении ошибок (False Positives / False Negatives) накапливается огромная база эталонных примеров. Если передать их все в системный промпт LLM, это приведет к:
1. Переполнению контекста (Context Window Overflow).
2. Замедлению работы ИИ и сильному увеличению стоимости токенов.
3. Эффекту "размытия внимания" (Lost in the middle) — ИИ перестанет обращать внимание на правила.

## Решение: Двухуровневая Система Памяти (Two-Level Memory)

Вместо использования тяжелых векторных баз данных (Vector DB/RAG), мы реализуем эффективную SQL-систему маршрутизации контекста на основе **Ниш (Niche Codes)**.

### Уровень 1: Роутинг (Context Identification)

Здесь есть **два архитектурных подхода**, выбор которых зависит от баланса между точностью и стоимостью.

#### Вариант А: Роутинг по каналам (Наивный)
Каждое сообщение привязано к нише через канал (`MonitoredChannel.niche_code`).
* **Плюсы:** 0 дополнительных затрат токенов, мгновенная скорость.
* **Минусы:** Крайне низкая точность на практике. В чате по недвижимости могут искать аренду авто, а спамеры кидают крипту во все чаты подряд. ИИ получит правила по недвижке для крипто-спама, что приведет к галлюцинациям.

#### Вариант Б: ИИ-Классификатор (Рекомендуемый)
Первым шагом сырое сообщение отправляется в очень быструю и дешевую нейросеть (например, Llama-3 8B через Groq, которая стоит копейки и отвечает за 0.2 сек). Ее единственная задача — определить тематику сообщения из списка (или вернуть "SPAM_OTHER").
* **Плюсы:** Идеальная точность контекста. LLM получит эталоны и правила именно для той тематики, о которой написан текст, независимо от того, в каком чате он был опубликован.
* **Минусы:** Удваивается количество запросов к API (добавляется 1 легкий запрос перед основным тяжелым анализом).

#### Вариант В: Векторная Память (Семантический поиск - Embeddings)
Вместо жестких ниш, мы превращаем каждое сообщение в вектор (Embedding). При новом сообщении мы просто ищем математически похожие тексты в базе прошлых ошибок.
* **Плюсы:** Идеально находит паттерны. Если пришел новый вид спама про "инвестиции", система найдет 5 прошлых спам-сообщений про инвестиции, даже если они не привязаны ни к какой нише.
* **Минусы:** Требует подключения VectorDB (или pgvector) и отдельного API для создания эмбеддингов. Усложняет инфраструктуру.

### Уровень 2: Извлечение Контекста (Context Hydration)
Перед отправкой сообщения в LLM, сервер делает два легких запроса к базе данных:

1. **Динамические Правила (Summarized Rules):** 
   * Периодический фоновый воркер (Summarization Agent) раз в сутки собирает все исправленные ошибки по нише и просит LLM: *"Проанализируй эти ошибки и выведи 3 четких правила, как их не допускать"*.
   * Эти правила сохраняются в таблице `NichePromptRule` и подгружаются в промпт. Это сжимает знания из сотен примеров в пару абзацев.

2. **Последние Эталоны (Recent Exemplars):** 
   * Система делает запрос к `AIStudyExemplar` (базе ручных корректировок) с фильтром `WHERE niche_code = 'текущая_ниша'`.
   * Извлекаются ровно 6 примеров: **3 самых свежих ложноположительных** (спам, который ИИ принял за лида) и **3 ложноотрицательных** (лид, которого ИИ отрезал).
   * Эти сырые примеры служат как Few-Shot инъекция для пограничных случаев, которые еще не попали в сжатые правила.

## Архитектура Базы Данных (Обновления)

### 1. `AIStudyExemplar` (Существует)
Хранит сырые примеры.
* `raw_message_text` (Текст)
* `is_lead` (Правильный вердикт администратора)
* `niche_code` (Для Уровня 1 роутинга)

### 2. `DynamicNicheRule` (Новая таблица)
Хранит сжатые (саммаризированные) правила для ниши.
* `niche_code` (String, PK)
* `summarized_rules` (Text) — например: *"В нише аренды байков сообщения со словом 'прайс' — это всегда подрядчики, бракуй их."*
* `last_updated_at` (DateTime)

### 3. `DynamicStopword` (Новая таблица)
Хранит извлеченные стоп-слова для локального пре-фильтра (Gatekeeper).
* `keyword` (String, PK)
* `niche_code` (String, опционально)
* `is_active` (Bool)

## Пайплайн Обучения (Схема работы)

1. **Корректировка:** Администратор в TMA интерфейсе жмет кнопку *"Это не лид (Спам)"*.
2. **Сохранение:** API меняет статус в `AIEvaluationLog` и записывает копию сообщения в `AIStudyExemplar`.
3. **Извлечение Стоп-слов (Асинхронно):** Сервер просит дешевую LLM (Groq Llama-3) извлечь стоп-слово из этого спама. Слово сохраняется в `DynamicStopword`.
4. **Саммаризация (Раз в сутки):** Крон-таск берет новые записи из `AIStudyExemplar` по нише, генерирует новые правила и обновляет `DynamicNicheRule`.
5. **Анализ новых сообщений:** Приходит новое сообщение из ниши X. В промпт подставляются:
   * Базовый системный промпт.
   * `DynamicNicheRule` для ниши X.
   * 6 свежих `AIStudyExemplar` для ниши X.
   * Само сообщение.

Таким образом, ИИ получает **максимум релевантной информации** при **минимальных затратах токенов**, а локальный фильтр (Gatekeeper) становится умнее каждую минуту, отсеивая спам еще до обращения к LLM.
